# Windows 全新安装与在线更新

用户选择重新安装、从空世界开始，并要求提供停止 BAT 和 GitHub 更新渠道。新的安装包不迁移旧部署数据；后续在线更新保留届时已有的账号、世界、上传素材与配置。

## 安装与启停

- `install.bat`：自动申请管理员权限，要求解压到新的安装目录，接管能明确识别的旧 `FabulaUltima` 后台任务和相应防火墙规则。只复用旧运行环境，不导入旧世界。原目录文件不删除。
- `stop.bat`：停用开机任务，停止本安装目录的 FU 进程，数据保留。不会停止其他 Node 程序。
- `start.bat`：重新启用后台任务和开机自启，验证当前程序版本能响应。
- 建议固定安装路径 `C:\FabulaUltima`，公网 IP 由用户输入。继承 0.2.2 的父目录最小权限修复。

### 0.2.4：全新安装接管残留任务

0.2.3 遇到旧目录已删除、移动或缺少 `app/build-info.json` 时，会报“无法确认原后台任务属于 FU 安装”。旧 0.1.6 原包已有这个标识文件，问题是残留任务仍指向不完整的旧路径。此前测试只覆盖完整旧目录，遗漏了这个安装场景。

0.2.4 仅在 `install.bat` 的全新安装路径允许通过原任务记录识别：任务必须是根目录的 `FabulaUltima`，只有一个 Node 启动入口，参数和工作目录一致，任务说明严格匹配 `FU 独立站：旧目录`。随后沿用原有的进程范围与防火墙目录核对。普通启动、停止保持要求有效程序标识；标识文件存在但属于其他程序或已损坏时仍拒绝接管。错误信息包含实际路径，识别过程不创建或改写旧目录。

新增回归测试覆盖旧目录完全不存在、只剩数据文件、完整 0.1.6、错误任务名／任务路径／说明／入口／工作目录、错误或损坏的程序标识。数据文件保留检查及原启停测试通过。此修复属于安装器；已正常安装的服务器无需重装，网页在线更新仍只替换 `app`。

## 更新契约

- 大厅的“服务器管理”使用独立 `FU_ADMIN_KEY`，与世界密码、普通账号和 GM 建房钥匙分开。管理员凭据不进入前端包或 GitHub。
- `GET /api/admin/status` 查看本机版本、世界连接数与更新状态；`POST /api/admin/login` 验证管理密码；`POST /api/admin/check` 查询固定仓库正式 Release；`POST /api/admin/update` 提交选定的正式版本。更新需要所有玩家离开世界回到大厅。
- 用户确认同时支持手动与每天无人时自动更新。默认 `FU_AUTO_UPDATE=1`，世界连接为零且连续空闲 10 分钟才每日检查；网络请求完成后再次检查在线状态，再进入维护模式。网络故障一小时后重试。
- Windows 启动器保持父进程，子进程承载网页服务。更新先下载和验证 ZIP 的 SHA-256、逐文件清单与更新协议版本，再暂停服务，备份程序和世界数据，替换程序并检查新版健康状态。失败时恢复备份并启动旧程序。
- 更新中的写操作和进房请求暂停。只更新完整 ZIP 的 `app` 文件，包括官方文本；根配置、运行环境和上传素材不覆盖。若更新因进程退出而中断，下次启动由根目录内稳定的 `update-runner.mjs` 根据事务记录恢复上一版后提供服务，即使 `app` 尚未完整替换也可以恢复。
- 用户明确选择 GitHub 全部公开：发布程序源码、转换后的官方规则文本及完整发行包。GM 素材、账号、世界、`.env`、诊断报告不公开。

## 验证边界

已通过 Windows 定向测试和类型检查；隔离程序真实启动、完整 ZIP 解压替换、新版故障回退、半途退出恢复均通过。测试在更新前创建账号与带密码的世界，并保存素材；比较更新前后全部数据文件的内容散列与 `.env`，均一致。自动更新测试覆盖在线时不检查、空闲后检查、GitHub 返回时有人重进则推迟、重复请求阻止。服务控制测试真实停止隔离 FU 进程，并确认其他 Node 进程仍在。

云服务器的管理员提权、任务注册和公网访问需在用户服务器运行安装包后生效；本机测试不会替代云部署。
